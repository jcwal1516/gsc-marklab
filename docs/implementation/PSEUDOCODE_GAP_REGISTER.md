# Pseudocode Gap Register

This register records master-plan capabilities that are absent or only partially specified in the current pseudocode. An adjacent algorithm does not close a gap.

## Foundational and stable work intentionally outside the current pseudocode

- classical two-dimensional K/L and edge corrections;
- inhomogeneous K/L;
- classical pair-correlation and cross-process estimators;
- F/G/J and nearest-neighbour distributions;
- stable scalar/categorical mark functions;
- scalar autocorrelation, local maps, variograms, and covariance;
- core pathology geometry, interfaces, infiltration, and niches;
- stable clone/CNA import and basic clone geometry;
- product/workbench surfaces.

These remain prerequisites and are governed by the master plan.

## Material frontier gaps requiring new pseudocode before implementation

1. Bayesian nonparametric niche/domain models:
   - finite mixtures;
   - Dirichlet-process and Pitman–Yor mixtures;
   - HMRF/Potts models;
   - spatial topic models;
   - overlapping/soft niche models.
2. Cross-attention and transformer multimodal fusion (`EMB-PRED-02`).
3. Foundation-model execution/admission adapter (`DL-CORE`), including checkpoint, license, environment, provenance, calibration, and patient/site validation.
4. E(2)/SE(2)-equivariant learned tissue models (`EQ-01`).
5. General method-specific interval and coverage contract (`INF-01D`).
6. Full pathology-geometry/domain workstreams that are only partially represented by topology, resource, front, embedding, or atlas functions.
7. Exact backend and numerical-oracle selections for each external or approximate family.

## Authority-gated methods

The following must not be scheduled merely because pseudocode exists:

- spatial mediation;
- balanced OT as a public endpoint;
- native Rust implementations of mature external inference engines;
- causal methods without an eligible treatment/exposure design;
- 3-D or longitudinal biological claims before registration uncertainty is available.

## Closure rule

A gap is closed only when:

1. the master-plan requirement and workstream owner are unambiguous;
2. canonical pseudocode, assumptions, typed failures, diagnostics, oracle, simulation plan, complexity, and promotion/kill criteria are added;
3. `CANONICAL_SYMBOLS.md`, `REQUIREMENTS.md`, and `VALIDATION_LEDGER.md` are updated;
4. the addition is reviewed before production implementation begins.
