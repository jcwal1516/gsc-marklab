## Frozen identity and schema semantics

### Existing byte identity

- `ArtifactRef { kind, SHA-256 content digest, byte length }` remains source-compatible and continues to identify exact encoded bytes for B-04.
- Add strict lowercase 64-hex parsing for `ContentDigest`; malformed/noncanonical text is rejected.

### Schema-bound identity

- `ArtifactSchema` is a bounded exact identifier plus a positive `u32` version. Identifiers use 1–128 ASCII alphanumeric, `.`, `-`, or `_`; no filename, media type, or version inference occurs.
- `ArtifactRecord` owns one existing `ArtifactRef`, one schema, an optional `TableManifest`, sorted unique dependency `ArtifactId`s, sorted bounded semantic metadata, and one or more portable locators.
- Compute `semantic_digest` with tagged, 128-bit-length-framed SHA-256 over content kind, schema, table declaration, dependencies, and semantic metadata in canonical order.
- Compute `ArtifactId` with a separate `marklab-artifact-id-v1` domain over schema ID/version, exact content digest/length, and semantic digest. Same bytes under a different schema/version/semantic manifest produce a different ID. Location never affects ID.
- Catalog construction rejects duplicate IDs, recomputation mismatches, missing/self dependency IDs, and dependency cycles. Validation order is fixed: syntax/bounds and duplicate claimed IDs; missing/self dependencies; iterative deterministic cycle detection; then semantic-digest and artifact-ID recomputation. This ensures a hostile cyclic manifest is rejected as a graph violation even when its content-derived claimed IDs are also forged.
- Location changes can add a replica without changing scientific identity. Re-registering an ID requires every non-location field to agree exactly. Locator sets are canonicalized by `StoreId`; an identical locator is idempotent, a locator for a new store is unioned, and a different locator for an already-bound store is a typed conflict.

## Immutable table declaration

- `TableFormat` is exactly `ArrowIpcFile` or `ParquetFile`. Arrow IPC stream is not a durable random-access file declaration.
- A `TableManifest` records format, a bounded explicit encoding-version string, exact row count, ordered unique columns, and a non-empty ordered unique primary key.
- Column types are a closed minimal set: Boolean, signed/unsigned 64-bit integer, float32, float64, UTF-8, binary, and fixed-size lists of one scalar type with positive length. Schema-specific later tasks may add reviewed types.
- Primary-key columns must exist, be non-nullable, may not repeat, and must use an exact scalar type: Boolean, signed/unsigned 64-bit integer, UTF-8, or binary. Floating-point and fixed-list keys are rejected because NaN/signed-zero/vector equality is not a stable durable-key contract. Zero rows are structurally representable; a scientific table schema may reject emptiness later.
- Exact compatibility compares format, encoding version, row count, column order/name/type/nullability, and key order. Extra/missing/reordered columns are mismatches.
- This declaration does not claim an arbitrary file physically matches it. C-04/WS-25 must parse Arrow/Parquet metadata under bounded readers and compare the observed declaration before use. Existing compatibility Parquet is not silently relabeled canonical.
- Apache Arrow distinguishes the random-access IPC file (footer and `ARROW1` markers) from its stream protocol; Parquet files place schema/row-group metadata at the file tail. C-03 therefore treats a fully closed file as the digest unit and publishes no partial file. Primary references: [Arrow columnar/IPC specification](https://arrow.apache.org/docs/format/Columnar.html), [Parquet file format](https://parquet.apache.org/docs/file-format/).

## Portable locations and object-store boundary

- `StoreId` is a 1-128 byte `[A-Za-z0-9_.-]` logical binding name. `ArtifactKey` is normalized portable UTF-8 with `/` separators, no empty/`.`/`..` component, absolute path, backslash, colon/drive/UNC form, control character, or over-limit component/path.
- `ArtifactLocator { store_id, key, optional object_version }` contains no absolute host path, endpoint, query, credential, or secret. The optional version is a 1-255 byte ASCII alphanumeric/`.`, `-`, `_`, or `:` provenance token, never an authorization value.
- A catalog is portable: runtime configuration binds a `StoreId` to a local capability root now or a future object-store adapter. C-03 adds no network call, cloud SDK, URL parser, credential loader, async runtime, or `object_store` dependency.
- Managed local keys are derived solely from `ArtifactId` under `objects/sha256/<prefix>/<full-id>`. External reference-only keys may be declared but cannot be overwritten by the managed writer and may not enter the reserved `objects/`, `.marklab-staging/`, `.marklab-quarantine/`, or exact `.marklab-store.lock` namespaces. A decoded managed locator is valid only when its key exactly matches the record ID.

## Canonical catalog manifest

- Format is `marklab.artifact_catalog`, version `1`; no prior durable format is claimed.
- `ArtifactCatalog::to_canonical_json` emits strict deterministic UTF-8 JSON from validated domain values, sorted IDs/metadata/dependencies/locations, and one final newline. Each serialized snapshot is immutable; the in-memory catalog may grow only through validated insertion and replica union.
- `from_json` rejects unknown fields, duplicate semantic declarations, invalid IDs/paths, oversized input, unsupported version, ID/semantic-digest mismatch, missing/self dependencies, and cycles. `from_canonical_json` additionally requires byte-for-byte canonical fixed-point equality.
- Old/future versions return `UnsupportedCatalogVersion`; C-03 does not invent a migration from a format that never existed.
- Fixed bounds: catalog JSON at most 16 MiB; at most 100,000 artifacts, 16 locations/artifact, 4,096 columns/table, 256 semantic metadata pairs/artifact, 4,096-byte metadata values/keys, and 4,096-byte artifact keys. Constructors enforce the closest tighter identifier/component limits.
- Semantic metadata keys use 1-128 bytes of `[A-Za-z0-9_.-]`; values are at most 4,096 UTF-8 bytes, contain no control characters, and reject a leading `/` or `\\`, an ASCII drive prefix, `://`, or `?`. Metadata and `object_version` carry privacy-reviewed provenance only, never credentials, authorization tokens, absolute patient paths, endpoints, or query strings.
- Catalog decoding never reads referenced artifact bytes or contacts a store. A valid catalog entry is only a declaration: it is neither available nor verified until a bound store successfully verifies the referenced regular file.

## Capability-scoped local store

- `LocalArtifactStore::open` is the single ambient-authority crossing. It rejects a symlink or non-directory root, then retains a `cap_std::fs::Dir` capability and one `StoreId` binding.
- The store creates one empty reserved `.marklab-store.lock` coordination file. Every publisher holds a cross-process shared `std::fs::File` lock; recovery holds the exclusive lock, so cooperative store instances cannot quarantine an actively written staging inode. Locks are advisory with respect to code that bypasses this API, which remains part of the trusted-root/operator boundary.
- Every key operation is descriptor-relative. Lexical guards give deterministic traversal rejection; capability resolution prevents `..`, absolute, and symlink escapes at the syscall boundary. C-03 also rejects any observed symlink component/final leaf to avoid location aliasing. The configured root itself must not be concurrently administered by an untrusted actor; no stronger host sandbox claim is made.
- Verification streams a regular file into the existing SHA-256 writer and checks both digest and length. Missing, mutated, truncated, appended, denied, wrong-store, directory, FIFO/socket/device, and symlinked artifacts are typed integrity errors, never ordinary cache misses.
- Managed publication writes a unique regular file beneath `.marklab-staging`, hashes only successfully written bytes, flushes and `sync_all`s, verifies expected identity, and creates parent directories. It then publishes with `Dir::hard_link(staging, destination_dir, leaf)`, whose existing-destination failure provides atomic no-replace behavior on the same filesystem. It syncs the destination directory capability, unlinks staging, and syncs the staging directory. Existing verified identical content is idempotent; conflicting content is never overwritten. If any supported target cannot provide hard-link plus directory-sync semantics through the reviewed safe capability API, stop rather than weaken the contract.
- Any ordinary callback/digest/prepublication failure leaves no final target and cleans only its task-created staging file. Ownership is armed only after atomic `create_new` succeeds, so a colliding writer's file is never removed. A failure after successful publication reports a typed `PublishedButCleanupFailed` state and never removes the durable target. Panic cleanup is RAII best effort. A crash may leave staging state; exclusively locked recovery moves only recognized regular staging entries into `.marklab-quarantine`, syncs both directories, and reports every move. Partial-state issues name any quarantine target already created. Recovery never follows symlinks or unrecognized/non-regular entries and reports them without deletion.
- C-03 does not publish a mutable project head. Catalog manifests and objects are immutable artifacts; atomic mutable project snapshots/execution-ledger heads remain a later WS-11 task.
- `OutputWriter` and its current output paths remain unchanged.
- `cap-std` is selected because its Bytecode Alliance capability directory defends multi-component paths and symlink escapes across supported platforms without adding unsafe code to Marklab. Primary source: [cap-std capability model](https://github.com/bytecodealliance/cap-std/blob/main/README.md).

## Complexity and resource contract

- Artifact identity is O(size of semantic declaration), not O(content bytes after the `ArtifactRef` digest exists).
- Catalog construction/encoding is O(n log n + total metadata) for deterministic ordered maps/sets; dependency validation is iterative and output-size bounded.
- Store write/verify is O(content bytes) time and fixed-size buffer memory. It never materializes a large artifact.
- Catalog JSON is bounded before parse; table vector bytes never enter JSON.
- No deterministic-Parquet-byte claim is made across writer/library/settings changes. Exact bytes are identified only after a fully closed file is hashed.
