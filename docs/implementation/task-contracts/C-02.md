## Proposed semantics

### Frames, axes, and units

- A frame has one typed ID, an ordered unique spatial-axis list, one unit, and one space. Supported axis sets are exactly `{x,y}` or `{x,y,z}` in any declared order; values and matrix rows/columns always follow that order.
- `CoordinateUnit` is `Pixel`, `Nanometer`, `Micrometer`, or `Millimeter`. `Image` space requires `Pixel` plus an explicit `PixelCenterAtInteger` or `PixelCornerAtInteger` convention. `Physical` space requires a physical length unit. There is no default pixel-origin or unit inference from field/file names.
- A frame is 2-D or 3-D from its axis set. Coordinates carry their frame ID and fixed arity, reject non-finite values, and can be constructed only through a registry that verifies the frame dimension.
- Coordinate values may be negative. Pixel coordinates are continuous frame coordinates, not validated array bounds; integer raster bounds remain an adapter/storage responsibility.

### Directed transforms and explicit chains

- A `FrameTransform` has a typed ID, named source and target frames, a finite same-dimensional affine matrix, and an optional uncertainty reference. Six 2-D coefficients form a row-major 2×3 matrix; twelve 3-D coefficients form a row-major 3×4 matrix. Rows follow target-frame axis order, non-translation columns follow source-frame axis order, and translation is expressed in the target unit.
- Source and target units may differ only through this explicit named map; coefficients must encode unit conversion and anisotropic calibration. C-02 performs no implicit conversion and never synthesizes identity or `1.0 micrometer/pixel` calibration when MPP is absent. Pinned `wsi-rs` exposes optional per-axis MPP, and nine inventoried selected slides lack usable physical scale; absence of a pixel→physical transform is the required unavailable state.
- The registered transform graph is acyclic. Missing frames, duplicate IDs, self edges, dimensional/matrix mismatches, missing or wrongly framed uncertainty, and cycles are typed errors selected in input order. Iterative tri-color DFS visits frames and each frame's outgoing transforms in declaration order and reports the first encountered back edge.
- Transform application receives an explicit ordered chain of transform IDs. Each next source must equal the prior target; no shortest path, inverse, ambiguity resolution, or filename/name matching occurs. An empty chain retains the coordinate unchanged.
- The registry can require an exact dimension or physical space for a method boundary. Asking for 2-D against a 3-D frame is a typed `DimensionMismatch`, not projection or truncation; a pixel coordinate retained by an empty chain cannot satisfy a physical-frame boundary.
- Chain application returns only the transformed coordinate. It does not sum, compose, or propagate conservative radii; edge uncertainty references remain inspectable metadata until a later reviewed propagation model.

### Uncertainty references

- An `UncertaintyReference` has a typed ID, the frame in which it is expressed, and an optional finite non-negative conservative radius in that frame's declared unit. `None` means no scalar bound is available, never zero uncertainty.
- A transform's uncertainty must exist and be expressed in its target frame. C-02 stores no covariance/displacement field bytes and makes no probability-distribution claim; C-03 owns the referenced artifact and provenance.

### Serial sections

- A `SerialSection` declares `SectionId`, ordinal, signed finite z center, positive finite thickness, state, and optional `SerialSectionPlacement`. Z and thickness use the enclosing 3-D volume frame's physical unit.
- A placement names the intrinsic physical 2-D source frame, six finite row-major 2×3 coefficients mapping source coordinates into the target volume's semantic X/Y coordinates, and optional placement uncertainty. Rows are target semantic X then Y, columns follow source-frame axis order, and translations use the volume unit. This specialized dimension-changing relation is not a same-dimensional `FrameTransform` DAG edge.
- `Observed` requires placement and permits optional uncertainty; `Missing` requires no placement/uncertainty and is how a gap is represented explicitly; `Distorted` requires placement plus uncertainty expressed in the target 3-D volume frame. No same-cell correspondence is implied.
- A `SerialSectionSeries` names one physical 3-D volume frame and contains a non-empty input-ordered sequence with unique section IDs, consecutive ordinals, and strictly increasing z centers. Each placement source frame must be physical 2-D and use the volume frame's unit; placement uncertainty must exist in the target volume frame.
- The first ordinal may be any `u32`; every next retained entry must equal the checked prior ordinal plus one. Positive thickness does not imply contiguous tissue: variable gaps and nominal overlaps remain representable, and no spacing or missing-section position is inferred.
- The registry embeds a present section's framed 2-D coordinate by applying its explicit placement to semantic volume X/Y, inserting the declared z center, and assembling the result in the volume frame's axis order. The supported model is parallel serial sections; it performs no inferred transform, interpolation, oblique-plane mapping, or correspondence.
- A registry rejects duplicate volume-series ownership and repeated section IDs across series. It does not interpolate missing sections or construct a 3-D observation window.

## Deterministic validation and complexity

- Error phases: local ID/value definition; duplicate frame/uncertainty/transform declarations; missing and incompatible references; transform cycle; serial-series local shape; serial cross-reference validation; coordinate/chain application.
- Construction target is expected O(frames + transforms + uncertainties + serial sections) time and retained state. Cycle checking and chain application are iterative; no recursive stack growth. Error selection follows declaration order, never hash iteration.

## Required behavior-first tests

1. All three new IDs reject blank, surrounding-whitespace, control-character, and over-limit values while retaining exact opaque text and typed distinction.
2. Frames accept 2-D/3-D axis permutations but reject duplicate/incomplete axes, image/physical unit mismatch, and an unspecified image convention.
3. Duplicate/missing frames, transforms, uncertainties, and wrong-frame uncertainty references are typed failures; transform coefficients reject NaN/infinity.
4. Matrix and frame dimensions must agree; a method requiring 2-D rejects a 3-D frame.
5. Self edges and multi-node transform cycles fail deterministically; a deep chain/cycle-tail is iterative.
6. Explicit 2-D and 3-D chains apply exact known affine maps in declared axis order; include source `[y,x]`, target `[x,y]`, unequal semantic X/Y scales, and translation. Disconnected/out-of-order/missing chains fail rather than auto-selecting a path.
7. Coordinates reject non-finite values; an empty chain retains its pixel frame and fails a physical-frame requirement; no implicit unit conversion or missing-MPP fallback exists.
8. Serial sections reject non-finite/non-increasing z, non-positive thickness, duplicate/non-consecutive ordinals, duplicate sections, invalid state/frame/uncertainty combinations, non-3-D volume frames, non-2-D section frames, and unit mismatch.
9. An explicit missing section and a distorted section with target-volume uncertainty form a valid series without implying correspondence; absent scalar uncertainty remains distinct from zero. Explicit affine section placement honors both in-plane and volume axis permutations and rejects missing/wrong-frame coordinates.
10. Existing registration/API/result tests remain unchanged and passing; new source contains no fit routine or result/config 0.3 field.
